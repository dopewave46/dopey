Master Product Specification  /  Version 1

DopeOrca OS

The internal operating system for DopeOrca Technologies — a solo / small web design and development agency in Mumbai, India. One private dashboard for leads, clients, projects, tasks, invoices, payments, expenses, AMCs, and the numbers that tie them together.

This document defines scope, architecture, pages, features, data, and non-functional requirements for Version 1. It is the approved reference for build. No implementation begins until this is signed off.

Currency: INR ₹ Timezone: Asia/Kolkata Location: Mumbai, India Desktop-first · responsive Single admin
A — Product overview

A focused agency operating system

DopeOrca OS replaces scattered information — notebooks, WhatsApp threads, spreadsheets, loose documents — with one connected system. The owner opens it and immediately understands what is happening in the business right now: what is in flight, what needs attention, what has been earned, and what is still owed.

Product principle

Core rule

If a feature does not help the owner run the agency, it is not built. Simple enough for one person to operate every day; powerful enough to run the entire agency.

The product deliberately does not aim to become Salesforce, HubSpot, Jira, Monday.com, QuickBooks, or an ERP. It is narrow by design: a premium, minimal, technical tool for one specific agency.

What Version 1 delivers

  • A dashboard that answers "what is happening today" at a glance.
  • A full lead pipeline, separate from clients, with conversion into client + project.
  • CRM with client profiles that aggregate projects, invoices, payments, tasks, and activity.
  • Project management with status stages and visual progress.
  • Simple task management scoped to today / upcoming / overdue / done.
  • Agency-focused finance: revenue, invoices, payments, expenses, profit.
  • Maintenance / AMC tracking with renewal visibility.
  • Readable analytics — every chart answers a real business question.
  • Useful, low-noise notifications and a fast global search.
  • A live Mumbai clock in the global header.

C — Information architecture

Structure

Primary navigation is a persistent left sidebar. Notifications and the live clock sit in the global top header, available from every screen. Detail views, tabs, drawers, and modals are used instead of proliferating pages.

Sidebar order for the ten primary destinations: Dashboard · CRM · Leads · Projects · Clients · Analytics · Finance · Tasks · Maintenance / AMC · Settings. Leads and Clients appear both as top-level sidebar items and grouped under CRM — the same views, reachable either way.

Global elements

  • Top header: global search, live Mumbai clock + date, notifications bell with unread count, admin menu.
  • Quick-add: a + action in the header opens a menu — Lead, Client, Project, Task, Invoice, Payment.
  • Command / search: keyboard-triggered global search across leads, clients, projects, tasks, invoices.

E — Features per page

What each screen does

Dashboard

Answers "what is happening in DopeOrca today?" Composed of six blocks plus quick actions.

  • Business metrics row: Active Projects · Total Leads · Active Clients · Revenue (received) · Pending Payments · Overdue Payments · Tasks Due Today · Active AMCs.
  • Project overview: counts for active, in development, awaiting client response, ready for deployment, recently completed — each links to the filtered project list.
  • Lead overview: pipeline counts — New · Contacted · Interested · Proposal · Negotiation · Won · Lost.
  • Finance overview: current revenue, pending revenue, overdue payments, expenses (period), estimated profit.
  • Task overview: today · upcoming · overdue · completed.
  • Recent activity: latest 10–15 events — lead added, lead converted, project created, project status changed, payment received, invoice created, task completed, client added.
  • Quick actions: + Add Lead · + Add Client · + New Project · + Add Task · + Create Invoice · + Record Payment.

CRM overview

  • Combined view of business relationships: recent leads, recent clients, upcoming follow-ups, and clients needing attention (overdue invoices, stale status).
  • Entry points into Leads, Clients, and Follow-ups.

Leads

  • Pipeline board (columns = stages) and table view, toggleable. Filter by stage, source, service, estimated value, follow-up date. Search by name / business.
  • Add / edit / archive lead. Drag or dropdown to change stage. Add notes. Schedule follow-up.
  • Lead detail: full fields, notes thread, activity history, follow-up schedule, Convert to client action (enabled on WON).

Clients

  • Searchable, filterable list (status, location, has active project, has overdue invoice).
  • Client profile: name, company, phone, email, location, website, status, date added, notes — plus tabs aggregating Projects, Invoices, Payments, Tasks, and a unified Activity timeline.
  • Actions: edit client, add project, create invoice, record payment, add task, add note, schedule follow-up.

Follow-ups

  • All scheduled follow-ups (lead + client) in one list, grouped Overdue · Today · This week · Later.
  • Mark done, reschedule, jump to the related lead / client.

Projects

  • List (table) and board (by status). Filter by status, client, deadline window, on-hold.
  • Project detail — Overview (value, client, dates, progress, requirements), Tasks, Timeline (status stage checklist), Finance (invoices + payments for this project), Links (GitHub / repo, staging URL, live URL), Notes.
  • Visual progress: stage checklist with per-stage completion, e.g. Planning ✓ — UI/UX ✓ — Development 75% — Testing — — Client Review —, plus an overall progress percentage.

Tasks

  • Four buckets: Today · Upcoming · Overdue · Completed. Optional grouping by project or priority.
  • Quick add (title + due date minimum). Inline status change. Filter by project, client, priority, status.

Finance / Revenue

  • Headline figures: revenue earned (invoiced), money received, money pending, overdue, expenses, profit — for a selectable period.
  • Breakdown by client and by month. Links into Invoices, Payments, Expenses.

Invoices

  • List with status filter (Draft · Sent · Pending · Paid · Overdue · Cancelled), client / project filter, date range.
  • Create / edit invoice, change status, record a payment against it, add notes. Invoice detail shows linked payments and outstanding balance.
  • Overdue is derived automatically from due date + unpaid balance.

Payments

  • List with filters (client, project, method, date range). Record payment (client, project, invoice, amount, date, method, reference, status).
  • Recording a payment updates invoice balance, client balance, and dashboard / finance figures.

Expenses

  • List with category filter and date range; period total.
  • Add / edit expense: name, category (Hosting · Domain · Software · Advertising · Equipment · Operations · Other), amount, date, notes.

Analytics

  • Revenue over time (monthly). Received vs pending vs overdue.
  • Leads created per month; lead conversion rate (won ÷ total closed).
  • Projects completed per month; active projects; average project value.
  • Expenses vs revenue; estimated profit trend. Client acquisition per month.
  • Period selector (last 3 / 6 / 12 months, YTD). No chart without a business question attached.

Maintenance / AMC

  • List of AMCs with client, project, service, start date, renewal date, payment status, hosting renewal date.
  • Renewal calendar / upcoming-renewals panel (next 30 / 60 / 90 days). Maintenance task checklist per AMC. Notes.

Notifications

  • Header dropdown (recent + unread count) and full page. Types: follow-up due today, task overdue, invoice overdue, AMC renewal approaching, project deadline approaching, payment received.
  • Mark read / mark all read; each notification links to its entity. Generated by scheduled server-side checks — no manual noise.

Settings

  • Agency information: name, logo, address, contact, invoice footer / terms.
  • Admin profile: name, email, password change.
  • Localisation: currency (default INR ₹), timezone (default Asia/Kolkata), date format.
  • Notification preferences: toggle each notification type; renewal / deadline lead-time in days.
  • Application preferences: default landing view, default list page size.
F — User flows

Primary flows

1 · Capture a lead

  1. Header + → Add Lead (available from any screen).
  2. Enter name, business, phone/email, source, service required, estimated value. Stage defaults to New.
  3. Save → lead appears in pipeline; activity logged.
  4. Optionally set a follow-up date in the same modal.

2 · Progress and win a lead

  1. Open Leads board → move lead across New → Contacted → Interested → Proposal → Negotiation.
  2. Add notes and follow-ups at each stage.
  3. Move to Won → "Convert to client" becomes available.

3 · Convert lead → client → project

  1. On a Won lead, click Convert to client.
  2. System pre-fills a client record from lead data; owner confirms / edits and saves. Lead is marked converted and linked to the client.
  3. Immediately offered: Create project — name, value (pre-filled from lead estimate), start date, deadline, requirements.
  4. Project created with status Planning; activity logged on lead, client, and project.

4 · Run a project

  1. Open project detail → add tasks, set deadline, record repo / staging / live links.
  2. Advance status through the stage list; update progress percentage.
  3. Create invoices against the project as milestones are reached.
  4. Mark Completed when live and paid; optionally create an AMC.

5 · Invoice and get paid

  1. From project or client → Create Invoice (client, project, amount, issue date, due date). Status Draft.
  2. Mark Sent → status becomes Pending; counts as revenue earned, not received.
  3. Record Payment against the invoice (amount, date, method, reference).
  4. When paid in full, invoice auto-moves to Paid; received revenue and client balance update. If due date passes unpaid → Overdue + notification.

6 · Daily check

  1. Open Dashboard → scan business metrics, overdue payments, tasks due.
  2. Open Notifications → clear follow-ups due, overdue items.
  3. Open Tasks → Today bucket → work through, mark complete.

7 · Track an AMC renewal

  1. Create AMC from a completed project (client, service, start, renewal date, hosting renewal).
  2. As renewal date nears, a notification fires per the configured lead-time.
  3. Owner records the renewal payment and rolls the renewal date forward.

I — Frontend requirements

Frontend

  • One coherent product. Every page uses the same shell, spacing scale, component library, and interaction patterns. No page looks like a different template.
  • Component library: app shell (sidebar + header), data table (sortable, filterable, paginated), card, metric tile, form controls, modal, drawer, dropdown / menu, tabs, badge / status pill, progress indicator, chart wrappers, toast, confirmation dialog, empty state, loading skeleton, error state.
  • Layouts: dashboard grid, list + detail, board (kanban), tabbed detail view, settings sections.
  • States for every view: loading (skeleton), empty (with CTA), error (with retry), populated. No blank or broken screens.
  • Forms: inline validation, clear error messages, disabled submit while pending, optimistic UI where safe, unsaved-changes guard on drawers / modals.
  • Live clock: header component rendering current time, date, and weekday for Asia/Kolkata, updating every second via a client timer — no page refresh. Format example: 7:03 PM — Monday, September 7, 2026 — Mumbai, India.
  • Global search: keyboard-openable overlay; debounced query; grouped results (Leads / Clients / Projects / Tasks / Invoices); keyboard navigable.
  • Currency & dates: all money rendered as ₹ with Indian digit grouping (e.g. ₹1,25,000); all times rendered in Asia/Kolkata.
  • Charts: lightweight library; simple, readable, labelled; palette-driven colours; no decorative-only charts.
  • Accessibility: semantic markup, visible focus states, keyboard operability for all primary actions, respects prefers-reduced-motion.
  • Suggested stack: a modern React framework (e.g. Next.js) with TypeScript, a utility CSS system, a headless component primitive set, and a typed data layer. Stack is a recommendation; the requirements above are binding.
J — Backend requirements

Backend

  • Authentication: email + password, hashed (bcrypt / argon2), session or JWT with secure httpOnly cookies. Single admin account seeded on setup.
  • API: RESTful (or typed RPC) endpoints for CRUD on every entity, plus aggregate endpoints for dashboard, finance overview, and analytics. Consistent error envelope and status codes.
  • Validation: server-side schema validation on every write; never trust the client. Enum values, required fields, numeric ranges, date sanity checks.
  • Business logic (server-owned):
    • Lead → client → project conversion, with linkage and activity logging.
    • Invoice status transitions; auto-Overdue when due_date < today and balance > 0.
    • Payment application: reduce invoice balance, flip to Paid when settled, update client balance.
    • Financial rollups: revenue earned, received, pending, overdue, expenses, estimated profit = received − expenses (period-scoped).
    • Analytics aggregations: monthly revenue, conversion rate, project throughput, average project value, acquisition.
    • Progress rollup from ProjectStage records.
  • Activity tracking: a central logger writes an Activity row on meaningful mutations (create / status change / payment / conversion / completion).
  • Notifications engine: a scheduled job (daily + hourly) evaluates rules — follow-ups due, tasks overdue, invoices overdue, AMC renewals within lead-time, project deadlines approaching — and creates Notification rows, de-duplicated per entity per day. payment_received is event-driven.
  • Search: a single query endpoint that matches across leads, clients, projects, tasks, invoices by name / number / key fields.
  • No fake data in production. All figures come from the database. Seed / demo data is clearly separated and never shipped to prod.
  • Suggested stack: Node / TypeScript server (framework API routes or a small dedicated service), a relational database, an ORM with migrations, a job scheduler for notifications.
K — Database requirements

Database

  • Engine: a relational database (PostgreSQL recommended) for the connected, transactional data model.
  • Tables: users, leads, clients, projects, project_stages, tasks, invoices, payments, expenses, amcs, amc_tasks, follow_ups, activities, notifications, settings. No table without a clear owner in this spec.
  • Keys & integrity: UUID or bigint primary keys; foreign keys with sensible ON DELETE rules (restrict for financial links, cascade for child checklists); enum columns or check constraints for status / stage / priority / category.
  • Indexes: on all foreign keys, on leads.stage, projects.status, tasks.due_date, tasks.status, invoices.status, invoices.due_date, amcs.renewal_date, activities.created_at, and search-relevant text columns.
  • Money: stored as integer minor units (paise) or NUMERIC(12,2) — never floats. Single currency (INR) in v1; a currency column may exist defaulted to INR for future-proofing.
  • Timestamps: created_at / updated_at on all mutable tables, stored in UTC, rendered in Asia/Kolkata.
  • Migrations: version-controlled, forward-only, reversible where practical.
  • Normalisation: 3NF for core entities; polymorphic activities and notifications are the only deliberate denormalised patterns.
  • Backups: automated daily backups with point-in-time recovery on the hosted database.
L — Authentication requirements

Authentication

  • Single admin account. No public sign-up. Account created via a one-time seed / setup step.
  • Email + password login; strong password enforced; passwords hashed with a slow KDF and per-user salt.
  • Secure session: httpOnly, Secure, SameSite cookies; reasonable expiry with sliding renewal; explicit logout clears the session server-side.
  • All application routes and all API endpoints (except /login and health) require an authenticated session — enforced by middleware, not per-page checks.
  • Brute-force protection: rate limiting and lockout / backoff on repeated failed logins.
  • Password change from Settings requires the current password. Optional (not required in v1): TOTP 2FA — architecture should leave room for it.
  • Role field present on the user record (admin) so future roles slot in without a schema change.
M — Design system requirements

Design system

Visual language: premium, minimal, modern, technical, confident, clean. Inspired by premium SaaS dashboards; an original DopeOrca identity — no copied branding, logos, or proprietary elements.

Colour

RoleDirection
Brand / primary actionCrimson red — used for brand marks, primary buttons, active navigation, key highlights, important states. Not for large fills.
SurfacesWhite and soft neutral grey — the dominant visual field, providing balance.
TextCharcoal / near-black for primary; mid neutral grey for secondary and metadata.
StructureVery subtle borders / hairlines and soft shadows to separate objects — spent by role, not stamped on everything.
SemanticDistinct positive / warning / critical colours for financial and status signals — separate from the crimson accent.

No heavy gradients. The interface is not "red" — crimson is an accent that carries meaning.

Typography

  • A single clean contemporary sans-serif family for the UI; a monospace family for data, IDs, labels, and metadata where it aids scanning.
  • Clear hierarchy: page titles → section titles → card titles → body → labels → metadata.
  • Large financial numbers are visually prominent (larger size, tabular figures, tighter tracking). No decorative fonts.

Components & spacing

  • Consistent spacing scale, corner radius, and shadow tokens. Rounded containers, generous but disciplined padding.
  • Reusable primitives (see section I). Tables, cards, and forms share one visual grammar across the app.
  • Status is encoded in shape + colour (pills, chips, stripes), not colour alone.
  • Light theme only in Version 1 — a single, fully resolved light palette. No dark mode or theme switching in scope.
  • Iconography: one clean line-icon set, used consistently.

O — Security requirements

Security

  • Secure authentication and session handling (section L). All routes and APIs protected by default.
  • Server-side input validation and output encoding on every endpoint; parameterised queries / ORM only — no string-built SQL.
  • Secrets (database URL, session secret, API keys) in environment variables only. No secrets, keys, or passwords committed to the repository. .env gitignored; an .env.example documents required keys.
  • HTTPS enforced; secure headers (HSTS, CSP, X-Content-Type-Options, frame-ancestors).
  • CSRF protection on state-changing requests; rate limiting on auth and search.
  • Safe error handling: user-facing messages are generic; stack traces and internal detail are logged server-side only.
  • Principle of least privilege on the database account; automated backups; dependency updates monitored.
  • Activity log provides a basic audit trail of significant mutations.
P — Performance requirements

Performance

  • Dashboard and list pages usable in well under a second on a normal connection; aggregate figures served from efficient queries (indexed, batched — not N+1).
  • Lists paginated / virtualised; filters and search debounced; no fetching data a view does not show.
  • Reasonable client bundle: code-splitting per route, charts loaded only where used.
  • Cache stable aggregates (e.g. analytics) with sensible invalidation on relevant writes.
  • Animation only where it aids understanding (state transitions, drawer open) — no heavy or ambient effects; respects reduced-motion.
  • Server-side pagination and filtering; the client never downloads the full table to filter locally.
Q — Future expansion considerations

Built to extend, not overbuilt

  • Team members: user role field already present; add assignment (assigned_user_id) to tasks / projects and permission checks later without restructuring.
  • Client portal (separate future product): project, stage, milestone, and file data is modelled cleanly so a client-facing read layer can be built on top. No client-facing UI is built now.
  • Multi-currency: currency column defaulted to INR leaves room; formatting is centralised in one utility.
  • Documents / files: entity-attached file storage can be added (projects, AMCs) via a single attachments table and object storage.
  • Invoice PDF / email sending: invoice data model supports it; generation and delivery are a later addition.
  • 2FA, integrations (payment gateway webhooks, calendar sync): possible later; not in scope now.
Guardrail

Leave hooks, not implementations. Do not build multi-user, portal, or integration features in Version 1.

R — Explicitly excluded from Version 1

Not building

  • Client-facing portal or any client login.
  • Multi-user roles, permissions, team assignment, per-user dashboards.
  • Full accounting: ledgers, tax filing, GST returns, balance sheets, double-entry, payroll.
  • Messaging / chat, comments threads, activity feeds as a social layer, mentions.
  • Automation builders, workflow engines, custom fields, custom pipelines.
  • Generic AI features, chatbots, "insights" that don't answer a defined question.
  • Email marketing, lead scraping, form builders, landing pages.
  • Time tracking / timesheets, Gantt charts, sprint / agile tooling.
  • Native mobile apps, offline mode, browser extensions.
  • Public API, third-party marketplace, webhooks out.
  • Overloaded dashboards, decorative charts, vanity metrics.
S — Version 1 success criteria

Done means the owner can answer these instantly

  1. How many active projects do I have?
  2. Which projects need attention (awaiting review, deadline near, on hold)?
  3. How many leads do I have, and where are they in the pipeline?
  4. Which leads need follow-up today?
  5. How many clients do I have?
  6. How much money has the agency made (earned vs received)?
  7. How much money is pending?
  8. Which invoices are overdue?
  9. What tasks do I need to complete today?
  10. Which AMCs or renewals are coming up?
  11. How is the business performing over time?
  12. What happened recently in the agency?

Plus: adding a lead, creating a project, and recording a payment each take under a minute; the app is one coherent product across every page; and no production screen shows fake or hardcoded business data.
